# 表情包系统重做

## 0. 为什么要重做

现在的导入只认**压缩包**：管理页的选文件过滤器甚至写死成
`arrayOf("application/zip", "application/x-zip-compressed")`，用户手里拿到的素材如果是别的形状，
第一下就被挡住。而素材的流通形态早就不以 zip 为主了 —— 见下一节。

管理侧也缺一半：只能"导入 zip / 批量删 / 清空"，没有新建包、没有单独添加一张、
没有改名、没有把一张挪到别的包、没有排序。用户拿到素材之后没法整理，只能整包重导。

## 1. 市面上实际是怎么发"表情包素材"的

手上两份真实样本（用户提供）拆开看：

| 文件 | 里面到底有什么 |
|---|---|
| `自嘲熊表情包 <20位数字ID>.pdf` | 共 5 页。第 1 页是**一张整页大图**：21 个表情排成 5 列的格子图（含标题"自嘲熊表情包"与右下角"小红书号:xxx"水印）。第 2–5 页**没有嵌图**，只有文字：每行是 `https://pic1.imgdb.cn/i/<id>.jpg` + 一句中文描述（"小猫额头贴着交叉创可贴…"） |
| `呆猫八条 <20位数字ID>.docx` | 26 个媒体文件（4 个 RGBA PNG + 22 个 JPEG，每张 120–1080 见方）。正文严格交替：`图片` → `图床 URL + 中文描述`；第一段是包名"呆猫八条" |

**为什么是 PDF + DOCX 这一对，而不是 zip：**

1. **平台限制**：小红书/抖音/微信里传 zip，手机端要么打不开、要么被压缩降质；PDF/DOCX 是手机原生可预览的；
2. **取图方便**：DOCX 里每张图是独立文件，用户在手机上"长按图片→保存"就能拿到原图，不需要解压工具；
3. **体积与更新**：正文只写图床链接（`imgdb.cn`），文档本身只有几百 KB，作者换图不用重发文件；
4. **可编辑**：DOCX 能改配文、能加说明，方便二创作者改；
5. 那串**20 位数字**是笔记/专辑 ID，用来溯源与批量回捞原图。

结论：**导入端必须同时吃下这四种形态** —— 压缩包、Office 文档（docx/pptx）、PDF（整页格子图）、
纯链接清单（从文本/剪贴板里把图 URL 捞出来）。

## 2. 设计

### 2.1 分层

```
识别            StickerImportFormat      文件名 + 魔数 → ZIP / DOCX / PPTX / PDF / 图片 / 文本
解析            StickerDocumentScanner   docx/pptx：按文档顺序取图 + 配对配文 + 去重
                StickerMontageSplitter   整页格子图 → 逐格矩形（纯像素算法）
                StickerUrlList           任意文本 → 图片 URL 去重清单
落库            StickerLibraryRepository 统一入口 importSources(...)
交互            导入向导：预览 → 勾选 → 命名 → 落库
```

识别与解析全部写成**不依赖 Android 的纯逻辑**，为的是能被 JVM 单测覆盖 ——
"格子图切歪了""配文配错一行"这类问题只有在测试里才钉得住。像素输入抽象成 `IntArray`，
Android 侧用 `PdfRenderer`/`ImageDecoder` 出像素再喂进来。

### 2.2 过滤规则（宁少不误）

| 规则 | 值 | 原因 |
|---|---|---|
| 最小边长 | 64 px | 低于这个多半是图标/角标；120 px 的合法小表情仍保留 |
| 极端长条 | 长宽比 > 4 | 标题行、水印、分割线 |
| 内容去重 | 字节 SHA-256 | 同一素材在 PDF/DOCX 里常重复出现 |
| 单次上限 | 200 张 | 与既有 zip 限制一致 |

### 2.3 配文怎么用

DOCX/PDF 文本里的中文描述（"小猫歪头（配文"我恨"）"）作为**候选名字**：
导入向导里默认填入，用户可以改。取不到就退回"包名 + 序号"。
图床 URL 记进 `来源`，用于"以后想换高清原图"时回捞。

## 5. 明确不做

- 不做"从微信数据库里把别人的表情扒出来"：那是别人的私有数据，也不在我们能访问的范围；
- 不在导入时自动联网抓原图：默认只解析本地文件里的内容，**下载必须由用户点**（一次几十张图、
  走的是外部服务器，静默做这件事既费流量也不可解释）；
- 不做 OCR 识别格子图里的文字：先靠形状切格 + 已有配文，切不对让用户在向导里删。

## 6. 实测：现有切格算法在真实样本上不合格（2026-11-04）

拿用户提供的那份真素材（`自嘲熊表情包 ….pdf`，第 1 页 21 格目录页）跑了一遍参数，
结论不客气但必须写下来：

| 指标 | 结果 |
|---|---|
| 真值 | 21 格 |
| 连通块法切出 | **10 块，通过尺寸筛选仅 9 块**，且面积从 540 到 71280（**差 132 倍**） |
| 失败原因 | 目录页贴纸之间空隙只有几像素，而块量化把空隙抹平了 → 多张并成一块 |
| 像素级投影法 | 10 行带 × 4 列带 = 23 个有内容交叉格（更接近，但仍有行被切碎、列几乎并成一条） |
| 按空隙比例合并带的变体 | ratio=0.2 时列带塌成 1 → 说明这套素材的**列间几乎没有空隙** |

**所以自动切格不能就这么上**：切出来是"几块装着半截表情的碎图"，导入比不导入更糟。

已经做的防护（有单测）：`StickerPdfPlanner` 加了 **格子面积必须彼此接近**（≤ 8 倍）的闸门，
不合格直接 Skip 这一页。真实样本正好落在这道闸之外（132 倍），因此现在导入这份 PDF 会得到
"没识别出可用表情"的明确提示，而不是一堆碎图。

下一期要做的：**按墨量谷值找网格边界**（列投影不再用"有没有内容"二值判断，而用密度低谷），
在样本上验到"切出 21 ± 2 格、面积差 < 8 倍"再放开这道闸。这一步不靠猜，先在样本上量。

顺带一条：这份样本第 1 页带 "小红书号: xxx" 水印，切格时它会被并入相邻格子——
真机核对时留意，必要时在导入向导里删掉那一格。

### 6.1 追加实测（同日）：细块与膨胀都不行

| 尝试 | 结果（真值 21 格，页面 990x1400） |
|---|---|
| 块 8px（原参数） | 22 块 → 合格 18，面积差 11.9 倍（多张贴纸并成一块） |
| 块 4px | 73 块 → 合格 24，差 12.0 倍 |
| 块 3px / 2px | 合格 25，差 5.5 / 3.2 倍 —— **但每格只有 82x100，占页 0.6%**：一张真贴纸应是 198x233（占页 3.3%）。也就是说"画"和它下方的"配文"被当成两块了 |
| 膨胀合并 15px | 直接并成 **1 整块**（贴纸之间空隙只有约 20px，比"画-配文"间距还小） |
| 膨胀 25 / 35 / 50 / 70px | 1–2 块，全部不可用 |

**判定**：连通块路线做不了这种密集目录页 —— 贴纸间距与"画-配文"间距同一量级，
任何膨胀半径都是"要么切开、要么全并上"。下一期要换成**周期性网格推断**
（先估行/列间距的 pitch，再按 pitch 铺格子），而不是继续在连通块上调参数。

本期先落一条能挡住碎片的实测规则：**每页最多 40 格，且每格至少占页面积 1.5%**
（碎片是 0.6%，真贴纸是 3.3%，分界清楚）。不满足就整页不收，并给出可读提示。

### 6.2 两段式布局上线（同日第三段）

按 6.1 的结论换成**先行带、再在每行带内按本行墨量低谷分栏**，在同一份样本上重跑：

| 项 | 结果 |
|---|---|
| 行带 / 列带 | 6 行 × 4~5 列 |
| 格子数 | 25（视觉核对为一格一张，前一版全局列带是 20 格且其中 5 格各含两张） |
| 单格尺寸 | 宽 62–131（中位 76），面积差 2.6 倍 |
| 单格占页 | 中位 0.7% |

两条由实测得出的修正：

1. **删掉"每格≥页面积 1.5%"的伪判据**：贴墨裁切本来就只有 0.7%，而上一期当作"碎片证据"的也是 0.6%
   —— 面积根本分不开"切准"和"切碎"，那条闸只会误杀好结果。
   留下的是"格子数 ≤40""面积离散 ≤8 倍"两条兜底；**准不准只能给人看**，所以导入向导是这条链的必要环节，不是可选项。
2. **行带要合并窄空隙**（绝对 ≤25px 且 ≤行高中位数 30%，双条件）：不然贴纸下方的配文会被当成独立薄带丢掉，
   用户拿到的表情少一行字。只按比例会真实页并把行并错（真实行间距约 38px > 25px，安全）。

新代码：`StickerGridLayout`（纯函数）+ 5 例合成密集页测试（**不放真实素材进仓库**：那是别人的作品还带水印，
回归资产要能说明它测的是形状而不是那张图）。

## 7. P3 导入向导（草稿 → 预览 → 勾选）

为什么这一环**必需**而不是锦上添花：6.2 量出来"切准 0.7% / 切碎 0.6%"，
面积、数量、离散度都分不开好坏。既然程序判不出来，就必须在入库前给人看一眼 ——
否则 PDF 导入等于"往库里扔一批可能切错的图，让用户自己去找哪些是碎的"。

流程：`prepareUri(uri)` 解析成草稿（`.drafts/<id>/` + `draft.json` 只存 token/文件名/配文）
→ 界面网格点选（默认全选，点一下取消）→ `commitDraft(id, keep)` 移动进正式库并删草稿
→ 取消则整目录删除。过期（1 小时）与没有清单的孤儿目录在启动时清掉，
不然用户只会发现"内部存储莫名多了几百 MB"，且看不到在哪儿。

只覆盖文档与 PDF：压缩包是用户自己的目录结构、相册多选是用户自己点的图，
都不存在"自动挑错"，仍走直接导入。`importUri`/`importDocument`/`importPdf`
结果不变（内部改成"解析草稿 + 全部提交"），所以自动化与分享入口不受影响 —— 有两条用例锁着。

命名/改配文沿用导入后的长按面板，没在向导里重复做一套。
