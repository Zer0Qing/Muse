### 方法论（这张表自己就是教训）

上一版我写"这些都被守住了"，依据只是"那个类有 N 个测试"。本轮逐条读用例名后：
**上一轮的结论是：3 条里 2 条本来就守着、1 条确实缺（已补）、1 条当时不知道**（FTS 顺序）。那条 ❓ 本轮已用实验收口（见下），没有留在糊涂账里。
三种结论都要能如实写出来 —— 尤其"不知道"要敢写，写"已守住"最省事但也最害人。

### FTS 顺序：从「不知道」做到「定性」（本轮实验）

上一版我把它标成 ❓ 并且**故意不写测试** —— 因为表里另有
`MessageFtsDdlTest > fts5 triggers keep insert delete and update in sync`，
提示"也许触发器已经兜住，顺序根本不重要"。给不存在的缺陷立碑，比不写更坏。

实验结果，两问同答：

1. **契约是真的**：`MessageFtsRuntime.useFts5` 默认值是 **`false`**（不是 true）——
   "顺序要紧"的 fts4 正是**生产默认路径**；`deleteFtsBySession` 的 SQL 是
   `DELETE FROM messages_fts WHERE message_id IN (SELECT id FROM messages WHERE sessionId = :s)`，
   等 messages 被级联删完再跑，子查询为空，**一行也删不掉**。
   表现不崩：「会话删了、搜索还搜得到它的消息」，点进去是一个不存在的会话。
2. **守卫有牙**：`SessionFtsDeleteOrderTest` 第一条是**前置自检**（确认 fts4 索引真被写过，
   否则"删完为 0"就成了恒真断言）；第二条是结论。把 `syncFtsDeleteBySession` 真的挪到
   级联删之后 → `2 tests completed, 1 failed` ✓ 随后还原产品代码并核与 HEAD 一致。

顺手把注释补准：原文只有"先删 FTS（依赖 messages 子查询，必须在级联删之前）"一句，
没说**为什么**、也没说 fts5 下这些 `syncFts*` 是空操作 —— 下一个人还得重推一遍。
现在两处删除路径（整会话删除、截断删除）都写清了两种模式的行为差异与实验出处。

一个值得记住的结构性事实：同一件"删索引"的责任，在 fts4 下由**应用层 SQL**承担（因此有顺序要求），
在 fts5 下由**数据库触发器**承担（因此没有）。这类"两种模式下责任方不同"的地方，
注释里不写清就一定会有人只测一条路径。

### 静默降级的第三条：`AutomationSettingsStore`（第 74 轮）

### 修对之后挖到的真问题：小手机一崩就崩整个应用

`MiniPhoneMomentsViewModel` 里 **8 个 `viewModelScope.launch` 一个 catch 都没有**
（`init` 首屏、加载更多、下拉刷新、发动态、点赞、评论、删动态、删评论）。
`generateMoment()` 内部有兜底，但 `repository.insertFromCharacter(...)` 和
`reloadFirstPage()` 的查询**没有** —— 异常会沿作用域冒到默认处理器：
**用户点个赞、刷一下动态，整个应用崩掉**（Room 忙、约束冲突、字段过长都够触发）。

新增 `launchGuarded(tag, action, onError)`（`io.zer0.muse.miniphone.ui`）并接到那 8 处，
两条约束写死在里面：

1. **`CancellationException` 原样抛回** —— 它是取消的正常信号，一起吞掉就等于
   把"取消"变成"静默不干活"，比崩更难查；
2. **不静默**：兜住的每个异常都带 tag + 动作名 + 原因进日志（用户看到的是"点了没反应"，
   日志里再没有，就永远查不下去）；`onError` 收尾自己失败也单独记一条。

顺带修了一个具体界面问题：`loadMore()` 先把 `isLoadingMore` 置 true 再启动协程，
原来一失败就**永远卡在"加载中"**；现在由 `onError` 收起。

`Error`（OOM、断言失败）**仍然照常往外冒**：它意味着 JVM 层面已经坏了，

### 第 90 轮（提交 `ba15cf96`）：一个**跨槽位误删**的真 bug

顺着第 89 轮那条轴继续读候选，读到 `ChatBackgroundStore` 时发现一处会丢用户数据文件的缺陷：

    if (n == base || (n.startsWith("${stem}_") && n.endsWith(".jpg"))) f.delete()

三层背景各有槽位文件名：全局 `chat_background.jpg`、深色全局 `chat_background_dark.jpg`、
会话 `chat_bg_session_<id>.jpg`；重新选图时还会留时间戳历史名 `chat_background_<millis>.jpg`。
"清理同槽位旧文件"的前缀判定用的是 `startsWith("${stem}_")` —— 全局槽位的 stem 是
`chat_background`，而 **`chat_background_dark.jpg` 恰好满足这个前缀**。

后果（用户可感知、且极难归因）：**清掉或重选浅色背景，会把深色背景的文件一起删掉**；
深色那边 DataStore 里存的 `file://…chat_background_dark.jpg` 还在，于是表现成
"深色模式莫名其妙没有背景"，而且没有任何报错。同一段判定在 `saveFromUri` 与 `deleteSlot`
**各抄了一份**，两条路径都会触发（选图时也会删）。

修法：

- 抽出唯一判定 `isSlotFile(name, base, stem)`：**时间戳历史名的后缀只可能是纯数字**，
  按"前缀 + 后缀全数字"认领，深色名（`dark`）不再被全局认领；
- 两处循环合并成一个 `deleteSlotFiles`（消灭"改一处忘一处"的形状）；
- 顺手补上这一族的留痕：单个文件删不掉不中断其余，但**失败数与异常都进日志**
  （磁盘上的孤儿文件用户看不见，只有查占用时会撞上）。

守卫 `ChatBackgroundSlotMatchTest` 5 例，核心那条直接命名为
「全局槽位不得认领深色槽位的文件（曾经的越界删除）」，另含会话 id 前缀关系
（`a1` 与 `a12`）不得互删、非 jpg 不认领、深色也不能反向删浅色。

**变异检验**：把判定退回旧前缀匹配 → 那条越界用例立刻 FAILED ✓（其余按预期仍绿），
回滚后读文件确认数字判定仍在。

### 第 92 轮（提交 `5ffe1fb0`）：把"原子写"这一形状扫完，修掉日志滚动两处

扫的是 **`renameTo` 的结果有没有被处置**（它失败是返回 false，不抛异常）。
全仓 35 处调用，**逐条读完**：12 处失败时按同一约定回退"复制 + 截断/再写"，
其余走 `check/require/error/返回失败` —— 也就是说仓库里本来就有清晰约定，
**只有 `Logger` 的日志滚动是那个不一致的例外**：

    file.renameTo(backup)      // 返回值丢掉
    writtenBytes = 0L          // 而 writerLocked 随后会把真实大小读回来

后果不是"日志丢一行"，而是**轮转永远不成功却每行都重试**：
关句柄 → 删备份 → 改名失败 → 重新开句柄，缓冲写退化成逐行落盘，
比不轮转还伤 IO；同时那个 1MB 上限形同虚设。

两处改动：

1. **轮转**：检查改名结果 → 失败按全仓约定回退"复制到备份 + 截断当前文件"；
   两条路都不行才记一条警告，并进入 60s 冷却（不再每行重试）；
2. **`initFileLog` 复位轮转状态**（这条是测试逼出来的、也是真缺陷）：
   它以前不关旧句柄也不清 `writtenBytes`。所以在**同一 JVM 跑多个测试类**时，
   上一个类写大的计数会带到下一个类，新文件第一行就触发轮转，
   把刚写的内容截掉 —— 表现就是 `LoggerOutletsTest` 莫名其妙变红。
   而生产侧同样有这个隐患：二次 `initFileLog`（换目录/重新启用）会把日志
   继续写进**上一个文件**，而 `logFile` 已经指向新路径。

新增 `LoggerRollingTest`：一个方法里按顺序走完"未到阈值不轮转 → 越过阈值轮转 →
当前文件仍被控制在阈值量级 → 最新内容不丢"。**为什么合在一条**：
`writtenBytes` 是对象级状态，拆成两条测试方法会互相继承计数，时好时坏 ——
这跟本仓库"进程级全局"是同一族问题，写测试时必须考虑进去。
覆盖边界也写明白：**回退分支没有被测到**（需要一个"改名必然失败"的稳定环境，本机造不出来），
不假装已覆盖。

`MAX_LOG_FILE_BYTES` 改成 `internal`，让测试引用同一个数而不是抄字面量
（抄一份就会在有人调阈值时变成假红/假绿）。

复查后判定：`:common` **74 例 / 0 失败**，并且**连跑三次全绿**（确定性确认，
不拿"跑一次绿"当结论）；`LoggerOutletsTest` 与 `LoggerRollingTest` 不再互相干扰。
