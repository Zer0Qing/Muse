### 方法论（这张表自己就是教训）

上一版我写"这些都被守住了"，依据只是"那个类有 N 个测试"。本轮逐条读用例名后：
**上一轮的结论是：3 条里 2 条本来就守着、1 条确实缺（已补）、1 条当时不知道**（FTS 顺序）。那条 ❓ 本轮已用实验收口（见下），没有留在糊涂账里。
三种结论都要能如实写出来 —— 尤其"不知道"要敢写，写"已守住"最省事但也最害人。

### FTS 顺序：从「不知道」做到「定性」（本轮实验）

上一版我把它标成 ❓ 并且**故意不写测试** —— 因为表里另有
`MessageFtsDdlTest > fts5 triggers keep insert delete and update in sync`，
提示"也许触发器已经兜住，顺序根本不重要"。给不存在的缺陷立碑，比不写更坏。

实验结果，两问同答：

1. **契约是真的**：`MessageFtsRuntime.useFts5` 默认值是 **`false`**（不是 true）——
   "顺序要紧"的 fts4 正是**生产默认路径**；`deleteFtsBySession` 的 SQL 是
   `DELETE FROM messages_fts WHERE message_id IN (SELECT id FROM messages WHERE sessionId = :s)`，
   等 messages 被级联删完再跑，子查询为空，**一行也删不掉**。
   表现不崩：「会话删了、搜索还搜得到它的消息」，点进去是一个不存在的会话。
2. **守卫有牙**：`SessionFtsDeleteOrderTest` 第一条是**前置自检**（确认 fts4 索引真被写过，
   否则"删完为 0"就成了恒真断言）；第二条是结论。把 `syncFtsDeleteBySession` 真的挪到
   级联删之后 → `2 tests completed, 1 failed` ✓ 随后还原产品代码并核与 HEAD 一致。

顺手把注释补准：原文只有"先删 FTS（依赖 messages 子查询，必须在级联删之前）"一句，
没说**为什么**、也没说 fts5 下这些 `syncFts*` 是空操作 —— 下一个人还得重推一遍。
现在两处删除路径（整会话删除、截断删除）都写清了两种模式的行为差异与实验出处。

一个值得记住的结构性事实：同一件"删索引"的责任，在 fts4 下由**应用层 SQL**承担（因此有顺序要求），
在 fts5 下由**数据库触发器**承担（因此没有）。这类"两种模式下责任方不同"的地方，
注释里不写清就一定会有人只测一条路径。

## 同类新线：静默降级不留痕（第 72 轮，提交见本节末）

按同一思路换了一类目标：**写操作失败被 `runCatching` 吞掉且一句日志都不留**。
扫描口径（脚本可复跑）：`app/memory/miniphone/conversation-core` 的 `src/main` 里，
守卫体内出现写语义（insert/update/delete/save/send/export/…），且上下 6 行内没有
`Logger`/`onFailure`/`onError`/`throw`；排除清理语义（`release/close/destroy/deleteRecursively`）。

结果：**110 处写语义被守卫包住，其中 56 处完全无日志**。逐条看过后分三类：

| 类别 | 数量级 | 处理 |
|---|---|---|
| 临时文件删除（`temp.delete()`、`.bak` 清理等） | 大多数 | **不动**：失败本来就无害，加日志只会淹掉噪声 |
| 自检/探测类（`execNode("-v")`、`availability()`） | 若干 | **不动**：拿不到就该显示"未知"，已有兜底文案 |
| 用户可感知的装配/发送路径 | 少数 | **本轮修一处，其余列在下表** |

### 已修：`agent_phone` 的群聊调度器懒解析

原写法（`AppKoinModule`）：

```kotlin
groupChatSchedulerProvider = {
    runCatching { get<GroupChatScheduler>() }.getOrNull()
}
```

`SkillAgentToolsImpl.execAgentPhone` 拿到 null 就回一句 `skill_agent_phone_not_configured`
（「未配置：GroupChatScheduler 未注入」）—— **日志里一个字都没有**。
测试环境该降级没错，但生产上装配真出错时表现是"悄悄发了但没人回"，
排查的人只知道"没配上"、不知道为什么，甚至不知道是没注入还是解析抛了。

改法（降级行为一字不变，只把故障留下痕迹）：

- 新增 `io.zer0.muse.util.lookupOrNull(label, lookup)`：仍返回 null、仍不抛，
  但失败时 `Logger.w` 带上**依赖名 + 原始原因 + 异常本体**；
- 装配点改用它；
- 工具侧把两种 null 分开说：**provider 没注入 = 装配漏接**（只能在这里归因）、
  **provider 有但取不到 = 原因见上游 `LazyLookup` 日志**。

守卫 `LazyLookupTest` 3 例，断言两面（返回 null + 一定留痕），并特意断言
"出口拿到的是脱敏包装件时**栈仍指向真正的抛出点**" —— 这是 `sanitizedThrowable`
的设计后果（它换对象但复制 `stackTrace`），以前只是注释，现在有断言。

**变异检验**：把 `lookupOrNull` 改回一行 `runCatching(lookup).getOrNull()` →
`3 tests completed, 2 failed`（两条"必须留痕"的用例红）✓ 随后从备份回滚。

### 这一轮我自己的两个操作错（都比代码问题更贵）

1. **对已跟踪但改动未提交的文件用了 `git checkout -- <file>`**：
   那是"变异后再还原"的标准动作，可它还原到的是 **HEAD**，于是当轮两处编辑被一起抹掉。

   正确顺序：**要么先提交再变异，要么先把自己的工作副本备份出去**（本轮从第二次变异起改成备份法）。
2. **新代码引入了一条 detekt 违规**（`LoopWithTooManyJumpStatements`：`?: continue` + `return@launch`）。
   没有用 `@Suppress` 绕，也没塞基线，而是把循环改成单出口（`if (socket != null) { … break }`）——
   顺带比原来更好读。墙外从 6 条回到 5 条（全部仍是他人文件）。

### 静默降级的第三条：`AutomationSettingsStore`（第 74 轮）

这个类五处解码失败，**只有一处打了日志**，其余直接 `.getOrNull()` 把原因丢掉。
逐个查了默认方向才敢动，因为它们的语义并不相同：

| 位置 | 解不动时的降级 | 用户看到什么 | 方向对不对 |
|---|---|---|---|
| 授权 flow | 当作「没有授权」 | 之前允许的自主行动又停下来重新问 | ✅ 宁可不放行，是对的 |
| 当日账本 flow | 今日 0 次 | 上限像没生效 | ✅ 只影响统计 |
| `incrementAutonomousRunCount` | 计数从 1 重启 | 当日上限可能多放行几次 | ⚠️ 方向可接受，但**必须能被解释** |
| 窗口配置 flow | 默认时段 | 「我明明开过」 | ✅ 已有日志（唯一一处） |
| `clearAutonomousAccessibilityGrant` | 不删除 | 旧值留着等下次覆盖 | ✅ compare-and-clear 不该盲删 |

所以修法是：**降级值一字不改**（这些方向本来就是对的），只把"从来没设过"和
"设过但解不动"分开——前者不打日志（否则每次读设置都刷屏），后者必留痕，
并且由调用方传一句 `consequence` 说清对用户意味着什么。以前统一一句
`decode failed` Even 不够用：授权丢失和账本重置的排查方向完全不同。

`AutomationSettingsDecodeTraceTest` 5 例，两条"没设过→不给日志"和"解不动→说清后果"
分开断言（前者防噪声、后者防静默，两者互相拉扯，必须同时钉住）。

**变异检验**：把 helper 改回 `runCatching { parser(raw) }.getOrNull()`（不记日志）→
**5 例红 4**，剩下那条例外正是"没设过不给日志"——它断言的就是无日志，理应继续绿 ✓
（如果它也被改红了，说明我的断言写反了）。

操作顺序这次是对的：**先备份自己未提交的改动 → 变异 → 从备份回滚**，
没有重演上一轮 `git checkout` 抹掉工作的事（回滚后核对与 HEAD 的差异仍是那 67/32 行）。
