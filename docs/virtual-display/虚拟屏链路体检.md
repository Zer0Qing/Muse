# 虚拟屏链路体检（`:virtual-display-protocol` / `:virtual-display-server`）

小手机多开、GUI Agent 独立屏、自动化截图都压在这条链上：
一个跑在 shell uid 的独立 APK（`Main` + `app_process`）持屏，主应用经 AIDL 调用。

## 0. 基线（实测，并纠正我自己的两次量法错误）

| 项 | 数值 |
|---|---|
| `:virtual-display-protocol` | **1 个 AIDL**（`IVirtualDisplayService.aidl`，28 行），无 Kotlin |
| `:virtual-display-server` | **6 个 Java**（`ServerService` 443、`FakeContext` 89、`BinderHandoff` 83、`Workarounds` 58、`Main` 65、`JpegQualityLadder` 38）+ 1 个 Java 测试 |
| 测试起点 | 5 例 / 0 失败（只覆盖 `JpegQualityLadder`） |
| 当前 | **9 例 / 0 失败**（提交 `c6116cb8`） |

我自己的错：**先用 `-Include *.kt` 再用 `-Filter *.kt` 都数到 0 文件**，差点把结论写成
"这两个虚拟屏模块是空壳"。真实原因是它们是 **Java/AIDL** 模块。
**规矩：数源文件要按各语言扩展名分别列，不能用单一后缀代替"有没有代码"。**
（同一轮里 `glob` 也连败两次：工作区根是仓库根，模式必须带 `1muse/` 前缀。）

## 1. 查过、写得对的地方（不动）

- `ensureDisplay` 只在**尺寸变化**时重建兼容屏（同尺寸直接复用并返回原 id），
  `destroyDisplayLocked` 会同步清 `compatibleDisplayId`；
- `MAX_ACTIVE_DISPLAYS = 3`，超额**拒绝并写日志**（不是静默返回 -1）；
- `requestScreenshot` **不在全域锁里等待**（v2.6.7 AUDIT F26 已修：旧实现整方法 `synchronized`
  + 最多 1 秒轮询，把 `ensureDisplay`/`launchApp` 全堵住，表现为"整个自动化卡住"）；
  取帧后再检查一次屏是否已被销毁，避免向死屏返回帧；
- `Image`/`Bitmap` 都有 `finally` 关闭/回收；`InterruptedException` 恢复中断位；
- 服务端 `launchApp`/`requestScreenshot` 故意抛 `IllegalStateException` 区分
  "屏 id 失效"与"还没出帧"，客户端 `catch (Exception)` 后走**"清缓存 + 刷新兼容屏 + 重试一次"**，
  独占屏则不越权替换 —— 这条自愈路径是对的；
- `launchApp` 对包名做正则白名单、`am start --activity-multiple-task` 的注释解释了
  为什么单靠 `--display` 会被任务复用回原屏。

## 2. 修掉的一处自相矛盾（提交 `c6116cb8`）

`JpegQualityLadder` 的注释与测试都写着"**永远给出一张图**，体积超一点只是传输慢一些"，
且阶梯退到底时**不再检查体积**就把字节返回。但 `createDisplayLocked` 允许 1920x2560，
那种帧在 q60 下仍可能超过 `MAX_JPEG_BYTES = 900_000`，而超尺寸 `byte[]` 过 Binder 是
**事务失败**（单事务约 1MB 上限）——客户端会把它当成"屏失效"去重建兼容屏，然后**同样失败**：
既没给到图，还多烧一次重建。那句"始终给一张图"因此不成立。

- 退到底仍超限 → 按 `SCALE_STEPS = {0.75, 0.6, 0.5}` **缩尺寸重编**（`chooseScale`
  取第一个放得下的系数，不一上来缩到最小：模型要看清字和数字）；
- 怎么缩都超限 → 按 AIDL 契约返回 `null`（协议注释本来就写"超时/失败返回 null"）并记明确日志；
- 探针每档创建的中间缩放图**当场回收**（否则一次截图漏 1-2 张 native 位图）。

测试 5 → 9 例，其中一条是**设计前提**：
`capStaysBelowTheBinderTransactionLimit` —— 有人为了"少退一档"把上限调大，
就会把"偶尔糊一点"变成"截图全废"，这条会先红。

## 3. 待查清单

| 候选 | 为什么 |
|---|---|
| `BinderHandoff`（83 行） | binder 手递手靠广播：主应用被杀/时序错乱时服务端会不会持着一个死客户端；有无超时兜底 |
| `Workarounds` + `FakeContext`（147 行） | 反射绕过隐藏 API 的部分在 Android 15/16 上的失效面（失效时的表现是否只是"截图没有"而不是崩） |
| idle 退出（15s）与重启 | 谁负责按需重启、重启期间的调用是否有队列；退出时显示的归属与销毁 |
| 真机验收 | 虚拟屏里输入法/横竖屏/高分屏 dpi 的实际观感，只能人眼看 |
