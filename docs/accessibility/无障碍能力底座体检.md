按"依次一个一个查"进入的模块：UI 自动化能力底座（手势、控件树、截图、输入），
小手机与协作链的"手和眼"都走它。

## 1. 查过、写得好的地方（不为"有产出"而改）

- **生命周期**：`onUnbind` 与 `onDestroy` **都**清 `connected`/`instance` 并广播监听器。
  注释给了实测依据：系统解绑时可能只调 `onUnbind` 而进程仍存活，只实现 `onDestroy`
  会让宿主以为"无障碍可用"，照发手势、读树，然后失败（API 36 模拟器上能看到
  "服务已连接 → Bound services 变空"的漂移）。这正是我一直找的"生命周期边界"类问题，
  这里**已经处理了**。
- **截图能力判定**：v2.6.13 起读系统真实上报的 `CAPABILITY_CAN_TAKE_SCREENSHOT` 位。
  旧实现反射去写 `AccessibilityServiceInfo.mCanTakeScreenshots` —— **AOSP 里根本没这个字段**
  （真机日志留了证据）。
- **控件树遍历**：`MAX_NODES = 500` 且 `dumpNode` 在循环里也检查上限（不是只在不检查就继续递归），
  超限写 `[truncated]` 而不是静默截掉；`root`/`child` 都在 `finally` 里 recycle。
- **密码字段**：`textForModel(isPassword=true)` 返回 `null` —— 保留控件元数据用于定位，
  但绝不把值或描述交给自动化模型。
- **手势/截图等待**：`CountDownLatch` + 超时，`dispatchGesture` 返回 false 立即失败，
  超时不会当成成功。
- `check(Looper.myLooper() != mainLooper)` 挡住主线程截图（fail-fast 有注释）。

## 2. 修掉的四处（提交 `6efe6ff0`）

| 处 | 问题 | 为什么算缺陷 |
|---|---|---|
| `findNodeByPath` | 路径指到一半 `getChild()` 返回 null 时 `?: return null`，**手上那个中间节点没 recycle** | 无障碍节点是 binder 引用；而 `path` 是**模型给的工具参数**，"指到一半没有"是常态输入而不是异常事件。服务长跑就攒下来 |
| `setTextOnNode` | `nodeId == "0"`（根路径合法）时定位到的就是 `root` 本身，于是内层 `target.recycle()` + 外层 `root.recycle()` **同一个节点还两次** | 语义错；现在 `if (target !== root) target.recycle()` |
| `parseNodePath` | 接受**负索引**（`"0.-1"` 能过） | 负数交给 `AccessibilityNodeInfo.getChild()` 是抛还是返回 null **取决于 ROM**。在纯函数层挡掉，让非法输入只有一种表现 |
| `escapeText` | 注释写"转义方括号"，代码**只转义 `]` 不转义 `[`** | 层级输出用 `[0.1.2]` 作节点前缀，文本里的 `[` 不转义会和前缀混在一起 —— 看的人（和读它的模型）分不清哪段是路径 |

测试加 2 例（负索引三种写法 + 根路径合法、左右括号都转义），
`:accessibility` 从 4 例到 **6 例**。

## 3. 证据边界（写清楚，别显得比实际强）

`:accessibility` 没有 Robolectric 依赖，测试只覆盖纯函数（`AccessibilityPathUtils`）。
所以 §2 里 **`findNodeByPath` 的漏还和 `setTextOnNode` 的双 recycle 是代码读查得出的结论，
没有跑到的用例** —— 它们要构造真实的 `AccessibilityNodeInfo` 树才行。
`parseNodePath` 的负索引守卫与 `escapeText` 有测试。
要真测服务本体得加 Robolectric + 假节点树，那是独立一步，不顺手塞。

## 4. 屏幕读不全时必须说清楚（提交 `e6f2dff4`）

这条是把待查清单里原来那两项（`AccessibilityExecutor` 口径 / `MAX_NODES` 截断语义）合并查完的结论，
改动落在 app 的自动化核心（读屏的生产者在那儿）。

**两种残缺以前是隐形的**：`toSummary` 会写"… 还有 N 个节点"（数量截断可见 ✓），但

1. 控件树被系统回收导致遍历中途抛异常 → 只 `Logger.w`，返回部分节点；
2. 深度超过 `MAX_TREE_DEPTH = 30` → `collectNodes` 直接 return，静默丢掉更深的控件。

两种情况在数据里都长得跟"一次正常读取"一样。于是模型把**「没读到」当成「屏幕上没有」** ——
表现为找不到控件、误点、或报告"界面上没有这个按钮"，用户看到的是"自动化在瞎说"。
**读数据的是模型，它看不见 logcat**：只写日志等于没写。

改法：

- `ScreenInfo.incompleteReason: String?`（`null` = 读全了；dumpsys/shell 等生产者用默认值）；
- 纯函数 `screenReadIssue(depthTruncated, error, collected, maxDepth)` 合成原因，
  两种残缺同时出现**都写**而不是相互覆盖；
- `toSummary` 把 `⚠ 本次读取不完整：…` 排在**控件清单之前** —— 位置是要害：
  模型读完前半截就可能已经决定点哪儿了，提示放末尾等于没放；
- `AccessibilityExecutor` 用 `CollectState` 记录深度截断，异常时记下原因与**实际拿到几个**
  （"只拿到中断前的 12 个控件"是可判断信息）。

顺带确认一条**不是缺陷**的怀疑：`AccessibilityExecutor` 用了 `textForModel` 但没 `escapeText`。
读下去发现它产出的是结构化 `UiNode`（进 JSON），不是行文本 —— 不需要转义。
（**读之前不下结论**这条本会话救了我很多次。）

测试 5 例：`读全了就不该出现警告行`（别把所有读屏结果都标残缺，那会让模型不信任数据）、
`残缺提示排在控件清单之前`（断言**顺序**而不只是存在）、
`深度截断与遍历中断各自都进原因`、`两种残缺同时发生时都写出来`、`默认构造不带残缺标记`。

`:app` 全量 **801 类 / 4590 例 / 0 失败**（800/4585 → +1 类 +5 例，逐笔对账吻合）。
证据边界：`AccessibilityExecutor` 里"残缺真的被填上"没有端到端用例（需要真实
`AccessibilityNodeInfo` 树），依据是代码读查 + 纯函数侧断言。

## 5. 手势坐标越界：原因要确定，兜底闸只放一处（提交 `957fec94`）

**查清的两件事**：

1. 越界**不会崩** —— Android 的 `dispatchGesture` 对外接不到的手势是**直接拒收且不回调**，
   上层只看到一个 `false`；
2. 真正的毛病是**原因传不到模型** —— 工具以前回一句
   「点击失败(坐标越界或通道未就绪…)」，两种完全不同的原因混在一起，
   模型分不清该「重新取坐标」还是「等权限就绪」，于是拿同一组坐标反复重试、白烧步数。

而且**校验原来只有一条路径有**：`isInBounds` 只存在于 `UiAgentRunner`；
模型直接调的 `screen_tap` / `screen_swipe` / `screen_pinch`、
定时工作流 `AutomationWorkflow`、`UIToolsSkill` **全都没闸**。

改法（措辞只有一份，`automation/core` 的纯函数）：

- `boundsIssue` / `pointsBoundsIssue` 给出**可照做**的信息：实际坐标 + 允许范围
  `0..W-1 / 0..H-1`；多点动作把**所有**越界点都列出来（只报第一个，模型改完还会撞第二个）；
- `AutomationManager.screenSize()` 走 `resources.displayMetrics`，**不读控件树**，
  所以每次动作前都查得起（用 `readScreen()` 拿尺寸是白付一次 UI dump）；
- 工具层在发出手势**之前**判：点击/滑动/缩放各自给确定原因；
  `screen_swipe` 的检查挪到读屏之前；`screen_pinch` 按**实际四个指尖**判
  —— 中心在界内不等于两指在界内（半距最大 1000px，靠边缩放指尖甩出屏外）；
- `AccessibilityExecutor.dispatchGesture` 加兜底闸：所有手势汇流到这一个函数，
  一处就覆盖三条入口，并写清楚具体范围。

**尺寸未知一律放行**：`width/height <= 0` 时返回 null。把"没量到屏幕尺寸"当成
"全都越界"会让自动化一个点都点不动 —— **那是把保护变成故障**。测试专门钉了这条。

测试 6 例（界内、边界外、尺寸未知、多点全列、空列表、原因含可照做的信息）。
`:app` 全量 **802 类 / 4596 例 / 0 失败**（+1 类 +6 例对账吻合），
筛选范围 automation+tools **1050 例 / 0** ⇒ 没有任何测试依赖旧文案。

一次编译期自错：`!path.computeBounds(box, true)` 被 Kotlin 当成非布尔（`!` 未解析），
改成副作用调用 + `if (box.isEmpty) continue`。

## 6. `:accessibility-provider` 查完：桥接是干净的，**配置才是问题**（提交 `34698bb2`）

46 行的独立 APK 为什么存在：无障碍服务是系统托管组件，拆出来单独授权后，
**主应用更新/重装/被杀时自动化能力不掉线**。查完的结论：

- 桥接本身没问题。`A11yProviderAccessibilityService` 只是共享实现的空子类，
  实例注册在基类 companion 的 `instance` 上；`A11yBridgeService` 逐个方法转发，
  **未连接时查询返回空串、操作返回 false** —— 与主应用内置实现同语义；
  `isAccessibilityServiceEnabled() = service() != null` 与 `connected` 标志等价
  （`instance` 只在 `onServiceConnected` 里赋值，`onUnbind`/`onDestroy` 都清）。
- AIDL 面只暴露**字符串层级**（`getUiHierarchy`），不含结构化节点 ——
  所以"provider 路径拿不到 resource-id"不是权限问题，而是**这条通道本来就没有 id 字段**。

### 真问题：同一个服务配置写了两份，而且已经漂了

| 属性 | `:accessibility` 的 `accessibility_service_config.xml`（provider 用） | 主 App 的 `muse_accessibility_service.xml` |
|---|---|---|
| `accessibilityFlags` | 缺 `flagReportViewIds` | 有 |
| `accessibilityEventTypes` | 缺 `typeViewTextChanged` | 有 |
| 三个能力位 / 节流 / 描述 | 同 | 同 |

**后果要说准**（我第一版把它说重了）：`viewIdResourceName` 的唯一读取方
（`AccessibilityExecutor` / `ScreenInfo.findBestViewIdNode`）只跑在主应用进程内，
用的是主应用那份配置，所以**今天不坏**。但"provider 优先、应用内兜底"是清单里写的迁移策略，
一旦哪天 provider 也要暴露结构化节点，缺的那位就会变成
「授权了却按 resource-id 点不动」——而配置错误在代码里**完全看不出来**。

处置：**收成一份**。`:accessibility` 那份补成超集（含 `flagReportViewIds` + `typeViewTextChanged`），
主清单改指 `@xml/accessibility_service_config`（app 已 `implementation(project(":accessibility"))`，
资源合并拿得到），删掉 `app/src/main/res/xml/muse_accessibility_service.xml`。

守卫 4 例（`AccessibilityServiceConfigTest`，读文件断言）：三个能力位在、
`flagReportViewIds` 不许被拿掉、**不许写 `packageNames`**（空串会被解析成"空包名过滤器"，
零事件送达 → `getCurrentActivityName` 恒空、`rootInActiveWindow` 为 null —— 这个坑配置注释里
早就写着，但没人钉）、主应用不再留第二份。

### 我这一轮差点写下的两个错

1. **误判"provider 资源缺失"**：我先看到 provider 自己的 `res` 只有 `values`，
   就下结论说它引用不到 `@xml/accessibility_service_config`。实际该资源由 `:accessibility`
   通过资源合并提供，而且根构建脚本一直在组装这个 APK —— 真去跑
   `:accessibility-provider:assembleDebug` + `:app:processDebugResources` 才发现我错了。
   **结论：**资源能不能解析，跑一次构建比读目录可靠。
2. **引用扫描把 `build/` 也扫了**：几十条过期产物噪音几乎让我把中间产物当活引用。
   规矩：这类扫描一律限定在 `*/src/*`。

验证：`:accessibility:testDebugUnitTest` **10 例 / 0 失败**（6→10）、`:accessibility:detekt` 0、
`:accessibility-provider:assembleDebug` 成功、`:app:processDebugResources` 通过。
