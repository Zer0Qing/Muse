# 无障碍能力底座体检（`:accessibility`）

按"依次一个一个查"进入的模块：UI 自动化能力底座（手势、控件树、截图、输入），
小手机与协作链的"手和眼"都走它。

## 1. 查过、写得好的地方（不为"有产出"而改）

- **生命周期**：`onUnbind` 与 `onDestroy` **都**清 `connected`/`instance` 并广播监听器。
  注释给了实测依据：系统解绑时可能只调 `onUnbind` 而进程仍存活，只实现 `onDestroy`
  会让宿主以为"无障碍可用"，照发手势、读树，然后失败（API 36 模拟器上能看到
  "服务已连接 → Bound services 变空"的漂移）。这正是我一直找的"生命周期边界"类问题，
  这里**已经处理了**。
- **截图能力判定**：v2.6.13 起读系统真实上报的 `CAPABILITY_CAN_TAKE_SCREENSHOT` 位。
  旧实现反射去写 `AccessibilityServiceInfo.mCanTakeScreenshots` —— **AOSP 里根本没这个字段**
  （真机日志留了证据）。
- **控件树遍历**：`MAX_NODES = 500` 且 `dumpNode` 在循环里也检查上限（不是只在不检查就继续递归），
  超限写 `[truncated]` 而不是静默截掉；`root`/`child` 都在 `finally` 里 recycle。
- **密码字段**：`textForModel(isPassword=true)` 返回 `null` —— 保留控件元数据用于定位，
  但绝不把值或描述交给自动化模型。
- **手势/截图等待**：`CountDownLatch` + 超时，`dispatchGesture` 返回 false 立即失败，
  超时不会当成成功。
- `check(Looper.myLooper() != mainLooper)` 挡住主线程截图（fail-fast 有注释）。

## 2. 修掉的四处（提交 `6efe6ff0`）

| 处 | 问题 | 为什么算缺陷 |
|---|---|---|
| `findNodeByPath` | 路径指到一半 `getChild()` 返回 null 时 `?: return null`，**手上那个中间节点没 recycle** | 无障碍节点是 binder 引用；而 `path` 是**模型给的工具参数**，"指到一半没有"是常态输入而不是异常事件。服务长跑就攒下来 |
| `setTextOnNode` | `nodeId == "0"`（根路径合法）时定位到的就是 `root` 本身，于是内层 `target.recycle()` + 外层 `root.recycle()` **同一个节点还两次** | 语义错；现在 `if (target !== root) target.recycle()` |
| `parseNodePath` | 接受**负索引**（`"0.-1"` 能过） | 负数交给 `AccessibilityNodeInfo.getChild()` 是抛还是返回 null **取决于 ROM**。在纯函数层挡掉，让非法输入只有一种表现 |
| `escapeText` | 注释写"转义方括号"，代码**只转义 `]` 不转义 `[`** | 层级输出用 `[0.1.2]` 作节点前缀，文本里的 `[` 不转义会和前缀混在一起 —— 看的人（和读它的模型）分不清哪段是路径 |

测试加 2 例（负索引三种写法 + 根路径合法、左右括号都转义），
`:accessibility` 从 4 例到 **6 例**。

## 3. 证据边界（写清楚，别显得比实际强）

`:accessibility` 没有 Robolectric 依赖，测试只覆盖纯函数（`AccessibilityPathUtils`）。
所以 §2 里 **`findNodeByPath` 的漏还和 `setTextOnNode` 的双 recycle 是代码读查得出的结论，
没有跑到的用例** —— 它们要构造真实的 `AccessibilityNodeInfo` 树才行。
`parseNodePath` 的负索引守卫与 `escapeText` 有测试。
要真测服务本体得加 Robolectric + 假节点树，那是独立一步，不顺手塞。

| 候选 | 为什么 |

| `:accessibility-provider`（46 行、**0 测试**） | 独立 APK：被系统绑定时桥接是否可靠；与主 App 服务的职责边界 |
