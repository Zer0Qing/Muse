## 1. 矛盾清单的静默数据丢失（提交 `c9b1faab`）

`MemoryContradictionStore` 是"记忆中心"里那份**给用户看**的清单：每日反思检测到
"它记得相反的两件事"就写进来，用户逐条确认或清除。

缺陷在读取的兜底：

```kotlin
runCatching { AppJson.decodeFromString(StoreData.serializer(), file.readText()) }
    .getOrDefault(StoreData())      // 文件不存在 与 文件坏了 —— 当成同一件事
```

于是任何一次 `save()`（读-改-写）都以"空表"为底，写出**只含本次 key** 的内容，
其它助手 / 其它空间的矛盾清单被整份覆盖，**不留任何痕迹**。
本类注释里其实早写着「随后 readAll 静默回退空列表，数据丢失」—— v2.6.2 只补了
锁与原子写（消灭了产生坏文件的主要来源），**坏文件之后的那条路一直没改**。

### 改法：沿用本模块自己的惯例

`io.zer0.memory.fact.FactDb` 早就立了规矩 —— **归档坏文件，归不了档就拒绝写**：

```kotlin
val renamed = runCatching { file.renameTo(bak) }.getOrDefault(false)
check(renamed) { "无法安全归档记忆库，已保留原文件: ${file.absolutePath}" }
```

照它做，不另造一套：

- 写路径（`save` / `clearScope` / `removePair`）走新的 `readAllForWrite()`：
  文件在但解不开 → 改名 `<名>.corrupt-<时间戳>` 留证据，再从空表重建；
  **改名失败就 `check` 抛出，拒绝这次写** —— 宁可停在原状，也不能覆盖唯一一份数据。
- 只读路径（`list`）保持宽容：按空表展示 + 一句 `Logger.w`，**绝不改动文件**
  （读不该有副作用，更不该顺手"重建"掉用户的数据）。

### 同类形状的全模块扫描结果

`getOrDefault(空)` 另有 6 处，都**不是**这个形状：

| 位置 | 为什么安全 |
|---|---|
| `FactStore:2351 / 2362` | 只读过滤，带 `onFailure { Logger.w(...) }`，注释写明"本次不剔除"的 fail-open |
| `FactStore:2588` | 逐行 tags 解析，只用于展示 |
| `MemoryEdgeBuilder:138` | 语义补边失败跳过，不落盘 |
| `NotificationMemoryDigest:146 / 185` | JSON 解析与计数，只读 |
| `LlmBudget:270` | tokenizer 计数失败给 -1 哨兵 |

文件写入方 `MemoryFileWriter` / `PinnedMemoryStore` 均已走"临时文件 + 原子 rename"。
**结论：静默覆盖在这个模块只有矛盾清单这一处**，不是系统性问题。

### 钉住它的 9 例（`MemoryContradictionStoreTest`）

两个 scope 互不覆盖；同 scope 不同 space 互不覆盖；space 留空落 `default`；
**坏文件在写之前被归档且归档内容一字节不差**；**只读遇坏文件不生成归档也不动原文件**；
`clearScope` 不误删同前缀 scope（`ab` 不删 `abc`）；空 scope 不清任何东西；
确认掉最后一对不留 `"pairs":[]` 空壳；未知 scope 的确认不报错。

其中"归档"那例在旧实现下**必红**（旧代码根本不产生归档）—— 有判别力的断言才叫测试。

## 2. 记忆空间：同名与重复序号（提交 `ae1a85e5`）

空间列表、切换器、记忆页「助手 · 空间」那行元数据**都只按名字展示**，所以仓储层两条松动会直接变成用户看错东西：

1. **同名空间被允许**：`createSpace` 不查重，`renameSpace` 也不查重 → 列表里两个都叫「工作」，
   用户只能靠逐个改名去猜哪个是哪个，猜错就把事实写进另一个空间。
   现在加 `findByName(name, excludeId)`（trim + 忽略大小写，改名时放过自己），撞名分别返回 null / false。
2. **重排只传一部分会留下重复 `sort_index`**：没被点到的空间留在旧序号上，而列表按
   `sort_index ASC, created_at ASC` 排 —— 撞车时先后取决于建得早晚，
   用户看到的现象是"我拖好了，一刷新又弹回原位"，而且没人报错。
   现在：无效 id 跳过；未列出的按原相对顺序接在后面；索引恒为 0..n-1 不重复；全是无效 id 时顺序不变。

`MemorySpaceRepositoryTest` 11 例（真内存库 `Room.inMemoryDatabaseBuilder(FactDb)` —— 这两条是
数据库层不变式，用假 DAO 测等于测我自己的假 DAO），含**删空间时事实迁回默认而不是被清掉**。

`:app` 全量 **799 类 / 4576 例 / 0 失败**（与收紧前逐项一致）。

## 3. 流程错：提交消息被我写成了生成脚本的源码

提交消息被我误写成了"生成脚本的源码"：前几轮的模式是 python 脚本内部再写 `msg` 文件，
这次我用 `write` 落了一个 python 脚本，**却没运行就直接 `git commit -F`** ——

**`-F` 的文件必须是纯文本消息**；如果走脚本生成，就要看到脚本自己打印的成功行，
并检查 `git log -1 --pretty=%s` 再收工。

## 5. 摘要提取丢掉重复标题段 + 提取提示词焊到解析器（提交 `a1cc7b5c`）

### 5.1 `extractMarkdownSection` 只取第一段

摘要是 `compileFacts` 的输入 —— **这里抽不出 facts 段，记忆里就直接少一批事实，而且不报错**。
旧实现找到第一个命中标题就 `return`。模型确实会把模板标题重复一遍（补一段「重要事实」），
于是第二段里的事实被**静默丢掉**；`validate()` 拦不住，因为它只看第一段是否为空，而第一段非空。
用户侧的表现就是"我明明说过，它不记得了"。

现在收集**所有**命中段，按行去重后保留首次出现顺序。顺带好处：第一段空、第二段有料时，
`validate` 也不再误报"正文为空"。

`RollingSummaryFormatTest` 9 例的做法值得记一笔：**先把这条跑红**
（`重复标题里的第二段也要在: - 第一条`），再改实现 —— 让实现自己说话，而不是读代码下结论。
其余钉住：中英两支抽取、1-6 级标题与大小写/尾随 `#`/多余空格、同级标题收尾而**更深层级子标题算正文**、
`- 无` / `* None` 判空、写前校验四类各拦一条、修复输入滤掉空白原因且不把草稿当指令、
**格式要求文案里的标题文本与实际解析词表同源**（看着像废话，却是
"模型照文案输出、解析端按另一份词表找 → 摘要永远抽不出事实"的成因）、空输入不抛。

### 5.2 `MemoryExtractPrompt` 的契约此前无人守

它是**实时自动保存记忆**那条路在用的（`MemoryAutoSaveScheduler:331 / :573`）。两处中文用户遇不到的形状：

- 中英两支各写一遍规则。今天对称，但没有任何东西保证明年还对称：某一支少提一个字段，
  解析端就拿默认值填上 —— 只有那个语言的用户会"说了没记住"。
- 解析用 `@Serializable`，JSON 键名就是属性名，所以"该提哪些键"的唯一真源是解析器本身。

`MemoryExtractPromptContractTest` 8 例把两边焊在一起：字段清单**直接取自
`ParsedAnalysis` / `ParsedEntity` / `ParsedLink` / `ParsedUpdate` / `ParsedMerge` 的
serializer descriptor**，将来加字段忘了写进 prompt 就立刻红（不手抄清单，抄的那份自己也会漂移）。
另钉：提取支与自动分类支的分类词表一致、`speaker` 三值都在（缺一个会把助手的话记成用户事实）、
两支都禁止 markdown 围栏且正文不出现 ```json、**未知/空 locale 落到英文支而不是给空提示词**
（否则那个语言的用户一条记忆都不再提取）、已有记忆预览为空时不留空章节。

实测结论：**今天没有漂移**（8 例全绿）—— 这组的价值是把对称性冻住，不是修当天的 bug。

## 6. 编译产物规范化：子分类被吃掉 + JSON 转义没还原（提交 `ef259e0a`）

### 6.1 `stripLeadingHeadings` 与它自己的注释相反

注释写着"保留正文中的子标题结构（例如 facts 段内的 `### Work` / `### Personal` 子分类）"，
实现却是**开头任意标题一律剥掉**：正文以子分类开头时第一个分类名被吃掉，
事实摊平成一大片 —— 用户看不出哪条属于哪类，模型注入的上下文也丢了分组。

现在只剥两类：命中段标题本身（`重要事实`/`Key Facts`/`事情经过`/`Timeline`，任意层级，
那是模型把外层标题复述了一遍）与 1~2 级文档前言（`# 摘要`、`## Overview`，是开场白不是内容）。
3 级及以上且不是段标题的，一律当正文留着。

### 6.2 JSON 数组转 bullet 时没还原转义

旧实现 `trim('"')` 只去外层引号，`"喜欢\"美式\""` 变成 `喜欢\"美式\"` ——
**反斜杠原样进记忆**：用户在记忆页看到的就是这串转义符，注入模型的上下文也带着。
改成真正的 JSON 解码；解不出来时保持原文不动，而不是半还原。

### 6.3 一个"在说谎的参数"

`normalizeLlmResult(value, source)` 的 `source` 被 5 处调用方传了有意义的值
（`compileFacts` / `compileToday` …）却**从未被读过**。没有删参数，而是让它真起作用：
剥掉围栏或 think 块说明模型没守输出契约，现在留一行带环节名的日志 ——
"记忆看着怪"时能直接定位是哪一步产出的。

### 6.4 顺手补的路由测试

`notificationCompileTarget`（21 行）的要点是"后台任务跑起来时前台助手可能已经切走"，
不能拿当前助手决定这轮记忆写进谁的库。4 例钉住：通知带来的助手优先、空白退当前助手再退主助手、
空间空白沿用当前空间、主助手 scope 恒为 `main`。**这段没发现缺陷**，是把行为焊住。

新增 14 例（`CompiledMemoryStateTest` 10 + 路由 4），JSON 那条**先跑红**
（`expected 喜欢["美式"] but was 喜欢[\"美式\"]`）再改实现；
并删掉换实现后没人用的 `JSON_QUOTED_RE`。

验证：`:memory` **391 例 / 0 失败**（377+10+4 逐笔吻合）、`:memory:detekt` 0 违规、
`:app` 全量 **799 类 / 4576 例 / 0 失败**（与基线一致）。

## 7. 中文连写的记忆搜索搜不到（提交 `8220922e`）

用户搜「笔记工具同步」，摘要里写着「在给一个笔记工具做同步层」，结果返回空 ——
他会以为"它不记得了"。

`compiledSearchTerms` 只按"字母/数字连续段"切词、不分词。英文靠空格天然切开；
**中文不打空格是常态**，一整句连写成了一个词，`contains` 只要措辞有出入就全落空。
原注释的理由（"切得比检索词更碎会放大误命中"）是对的，但代价全压在中文用户身上。

改法：**两轮匹配，第二轮只在第一轮一无所获时启用**

- 第一轮整词（现有行为一字不变，精确命中面不被搅浑）；
- 空手而归时，把够长的中文连写按相邻两字切分再找一次
  （两字是中文最常见词长；<4 字不切，"预算""同步"本身就是完整词；非中文不切）。

流水线抽成 `scanWith(sections, terms, limit)` 两轮共用。
新增 3 例：连写该捞到（**先跑红** `连写查询也该捞到相关散文: []`）、
整词命中时不启用兜底、确实无关的连写仍然不给命中。

顺带把新写法引入的 `ReturnCount`（5 个 return）改成两个 return 的 `when` —— 不抑制。

验证：`:memory` **394 例 / 0 失败**（391+3 对账吻合）、`:memory:detekt` 0 违规、
`:app` 全量 **799 类 / 4576 例 / 0 失败**。

## 8. 编译提示词契约与一个被排除的疑点（提交 `e7dc14fe`）

### 8.1 `CompilePromptsContractTest` 6 例：把中英对称冻住

五支编译提示词各有中英两支，编译产物**要注入回每一次对话**。实测今天没有漂移，
所以这组不是修 bug，是让下一次漂移立刻红。钉住：

- 每支 × 每语言都禁止 markdown 标题。**这条现在尤其要紧**：§6 把
  `stripLeadingHeadings` 收窄成"只剥段标题与 1~2 级前言"（为保住 `### Work` 子分类），
  "读的时候帮忙剥掉"这个保险就没了 —— 提示词那句从保险变成**唯一防线**。
- 条数上限中英**成对**（today/week `3 到 5`↔`3 to 5`、longterm `3 到 6`↔`3 to 6`、
  daily `两三句`↔`two to three`）：数字各写一遍就会各漂各的，用户看到的记忆长短
  取决于语言而不是内容。
- 未知/空 locale 必须与 `en-US` **完全相同**（不空白、不退回中文）。
- 中文支含汉字且与英文支不同（防"另一种语言直接复用英文"被当成正常）。
- facts 支要求"一行一条 / one fact per line"且不补"用户"主语（补了会让同一件事
  在 facts 与摘要里以两种写法各存一份，去重认不出）。
- `buildEditableFactsPrompt` 与 `buildFactsPrompt` 是同一份（别名，不许各自演化）。

### 8.2 删除墓碑的跨助手疑点：**排除**，不改

我曾怀疑 `clearLegacyTombstonesOnReset = key == "default"` 会让"重置主助手"抹掉
其他助手的旧删除标记，导致被删内容复活。读了调用方就不成立：

- `DataManagementScreen` 的"重置记忆"是**默认库 + 遍历所有 `facts_<id>.db` 分库**一起清
  （外加 daily/*.md、会话摘要、编译段），此时删共享 legacy 文件是对的；
- 删除**单个**子助手时 `key != "default"`，不碰共享文件；
- `getTombstones(scope, spaceId)` 会把"本 scope/space 现存事实"从墓碑里排除，
  跨助手的过度压制也被挡住。

结论：这条链成熟自洽，**不动**。记在这里，免得将来同一根线索再钓一次。

### 8.3 又一次假断言（当场删掉）

第一版"条数上限"写成 `map { if (it) "3 到 5" else "3 到 5" }` + `let { _ -> ... }` ——
**无论对错都通过**。这是本会话第 N 次抓到自己在写这种"看起来有断言"的行，跑之前就重写成
逐项 `assertTrue(contains(...))`。判据：**断言必须在实现出错时会红**，否则它就是注释，
不如删掉。

验证：`:memory` **400 例 / 0 失败**（394+6 对账吻合）、`:memory:detekt` 0 违规。

## 9. 默认 FactStore 被 new 了两份（提交 `1670db9c`）

`MemoryModule` 手工 `single { FactStore(...) }` 与 `FactDbProvider.getFactStore("default")`
并存 → **同一个 "default" 助手两个实例**。而这三样状态是实例级的：

| 状态 | 作用 | 双实例的后果 |
|---|---|---|
| `reconcileJob` | 写后对账的节流/合并窗口 | 同一次写入被两边各排一次，重复 DB/LLM 工作并彼此竞争 |
| `dedupMutex` | 同实体去重判定的串行闸 | **锁只在实例内有效**，两条并发写能同时进去重判定 |
| `ftsConsistencyChecked` | FTS 自检一次性标记 | 自检跑两遍 |

这类错不报错、跑很久才在数据上显形（重复事实、对账互踩）。改成复用 provider 那一份：
`single { get<FactDbProvider>().getFactStore("default") }`
（构造参数与 provider 完全一致：同文件路径、`assistantId = "default"`、`clearLegacyTombstonesOnReset = true`，
上游依赖没有增加）。

### 为什么必须测装配：装配错了应用**静默进安全模式**

`MuseApp` 把 `startKoin` 包在 `resultOf` 里，失败只标记安全模式；`MainActivity` 见 Koin 未启动
