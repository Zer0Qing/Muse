## 1. 结构性发现：这模块**一半接进应用、一半只在测试里活着**

用**大小写敏感**逐个类型数 `app/src/main` 的引用：

| 接进了应用 | 应用内 0 引用（只有本模块测试在用） |
|---|---|
| `ConversationCommand` 12、`ProviderEvent` 12、`RenderBlock` 12、`ConversationWindowReader` 4、`ToolExecutor` 2、`MarkdownBlockParser` 2、`CommandResult`/`SlotKind`/`ConversationAddress`/`SelectionSetId`/`CheckpointPort`/`CheckpointSnapshot`/`ToolInvocation`/`ToolOutcome`/`ToolRisk`/`PartKind`/`MessagePart`/`ConversationWindowSource`/`WindowSlotReference` 各 1~4 | **`DraftStore`、`ConversationRuntime`、`TurnRunner`、`CheckpointWriter`、`RenderDocument`、`CommandReceipt`** |

也就是说：命令/窗口/渲染那套合同是真在跑的；而"草稿投影 + 运行时 + 检查点写入"这套**带着测试但没有生产消费者**。

**我不动它，理由写清楚**（不是没看见，是判断过）：把应用的流式链路整体换到 `DraftStore`/`ConversationRuntime` 上是一项工程，不是缺陷修复 —— 涉及 `ChatViewModel` 的生成主路径，半接比不接更危险（会出现两套草稿真源）。这一条留作显式待办与产品决策项。

但"接上之前先把坑填平"是便宜且确定的，所以本轮修了它内部两处（见 §2）—— 否则接线那天带的就是**上线即崩**的性质。

## 2. `DraftStore` 的两处拒绝通道问题（提交 `5c643e7f`）

`apply()` 对外承诺的是**类型化结果**：非法输入给 `Rejected(reason)`，不抛。两处不守：

1. **`setMetadataPart` 用 `require(...)` 往外抛 `IllegalArgumentException`**：其余非法输入全走 `Rejected`，只有它抛；而投影侧没有 catch（`ToolExecutionAdapter`/`ConversationHost` 那层就是 `Rejected` 风格），一旦接上生产路径，一条"metadata 种类不支持"就是崩溃。现在改回 `Rejected(InvalidPart)`。
   顺带补一条同类守卫：**不能把已存在的正文/思考段就地改成带 metadata 的段**（`kind` 不匹配同样拒绝，与 `appendText`/`replaceText` 一致）。
2. **同身份重复 `Start` 被报成 `IdentityMismatch`**：此刻身份完全相等，报"身份不匹配"会把排查的人指向错方向 —— 与本会话刚修过的几处"把原因说错"是同一类。新增 `RejectionReason.AlreadyStarted` 并在此使用；真正不同身份仍报 `IdentityMismatch`。

`DraftStoreRejectionTest` 8 例：不支持的 metadata 种类返回拒绝而非抛出、已有正文段不被改 kind、同身份重启说 `AlreadyStarted`、不同身份才叫不匹配、正常 metadata 路径可增可改、未开始的内容事件 `NotStarted`、**回退序号 `IgnoredStale` 与重放序号 `Duplicate` 各归其类**、空增量被拒且**不吃掉序号**（同序号重试必须能生效）。

## 3. `EntryPolicy` 与执行协调器（提交 `da276a8f`）

**先量了一下使用面（大小写敏感）**：`ToolExecutionCoordinator` / `EntryPolicy` / `ApprovalPort`
在 `app/src/main` 里 **0 引用**，只有本模块的 contract test 在用 ——
所以现在是纠正成本最低的时刻，等接上流式路径再改就是拿运行期行为换。

1. `Proactive` 原先和 `MainChat` 一样全量放行，而 `Scheduled` / `Channel` 滤掉 High 风险工具。
   分档依据应是"**有没有人在这轮前面看着**"，不是入口名字：主动消息同样是应用自己起的轮次，
   高副作用工具（读屏、点击、发送、删除）在这种上下文出事，用户是事后才知道的。
   应用现状里后台单轮本就是"不授权工具" —— 这次是**把合同对齐到实现**，不是新决策。
2. `attemptedCalls` 无上限增长（每个工具调用进账永不出账）。改成 `LinkedHashSet` +
   上限 `MAX_ATTEMPTED_CALLS = 2000` 按插入顺序淘汰最早的；理由同 `:memory` 的墓碑表：
   宁可放过一次极旧的重复，也不让内存只涨不落。必须按插入顺序，否则"丢谁"不确定。
3. `Failed` 之后同一 `toolCallId` 仍占位、重试得 `AlreadyAttempted`：
   这轮把它写成**记录在案的取舍**（工具报失败时副作用可能已发生一半，自动重跑代价更大；
   真要重试由上层发新调用号）。

新增 4 例：三档入口策略矩阵（并断言 `Proactive` 与 `Scheduled` 同档）、人在场/远程两端、
失败后的重试语义、上限挤出后最早号可再跑而最近的仍被拦。
上限数字**由测试引用生产常量**（`internal`），不再抄第二份字面量。

本轮自己的三处返工：参数泛型被我打成 `List[ToolDescriptor]`（编译拦下）、
第一版用反射读私有字段证明有界（换成行为证明）、测试抄了一份上限导致引用断裂
（改成引用生产常量）。前两条都是"改完必须回读"的老账。

验证：`:conversation-core:test` **44 例 / 0 失败**（40+4）、detekt 0 违规、
`:app` 全量 799 类 / 4576 例 / 0 失败。

## 4. 命令校验的三处不对称（提交 `5c83c6fa`）

`ConversationCommand` 9 条命令一律"构造即校验"，但两处规矩与其余字段不同，且都刚好是能留下垃圾的那条：

| 位置 | 原来的规矩 | 后果 | 现在 |
|---|---|---|---|
| `Submit.text` | 只查 `isNotEmpty()` | 一串空格算合法提交 → 会话里多出一条看着是空的用户消息，占位、难认，删除还得先找到它 | 查 `isNotBlank()`，与其余字段同口径 |
| `EditUser.content` / `EditAssistant.content` | **完全没查** | 可以把已有消息编成空白气泡；用户本意通常是"删掉它" | 拒绝空白 |

"只发附件不发字"该怎么支持也写进了注释：**给 `Submit` 加附件字段并明确放宽**，
而不是靠空白文本绕开（那会让空消息合法化，而且看不出是有意为之）。

影响面先量过：构造 `Submit` 的唯一地方是 `conversation/ui/ConversationHost`，
而 **`ConversationHost(` 在 `app/src/main` 里没有任何调用点**（只有自身定义）；
`ChatViewModel` 完全不引用这些命令 → 收紧零风险，`:app` 全量 0 失败也证实无测试依赖空白命令。

`ConversationCommandValidationTest` 6 例：有内容合法、空白文本四种写法（`""`/空格/`\n`/制表）都不接受、
两类编辑不许编空白、命令 id 空白一律拒绝、会话 id 空白一律拒绝、
`ResolveApproval` 必须带全 `turnId`/`generationId`/`toolCallId` 三段身份。

一个实现细节：`Delete` 的 `init` 与两处编辑**文本完全相同**，所以补丁按 `data class X(` 划区域下手；
第一版用同文锚点被"命中 3 处"的断言挡下（守住了才没误伤），事后又单读确认 `Delete` 保持原样 ——
不是"应该没动"。

## 5. 本轮踩到的工具坑（第三次同类）

第一遍数引用时我用 `Select-String -Pattern '\bDraftStore\b'` 得到"app 内 7 处"，据此差点判定 `DraftStore` 是活的 —— 那 7 处其实是 `StickerLibraryRepository` 里的**变量 `draftStore`**：`Select-String` 默认**大小写不敏感**，`\b` 在 `draftStore` 前仍然成立。加 `-CaseSensitive` 后真实数字是 0。

这是本会话第三次被同一个默认值骗（前两次：数"零提及"文件时函数名不算文件名、注释里提一句也算覆盖）。**规矩：所有"谁引用了谁"的度量一律 `-CaseSensitive`，并且用大小写敏感的变量名歧义做一次反证。**

### 更正：`ProviderGenerationEvent.kt` 并不是「0 引用」（第四次同类坑）

§6 原来写它「全仓 0 引用」，那是**拿文件名去数**的结果 —— 文件里定义的类型叫
`ProviderEvent` / `ProviderEventType`，而 `app/src/main` 有 12 处引用 `ProviderEvent`
（`conversation/runtime/ProviderStreamMapper.kt`）。文件名 ≠ 类型名。

读完后结论是反的：这个文件是活的，而且映射器写得很好 —— `when (event)`
**没有 `else`、穷尽 10 种流事件**，将来新增一种就编译失败，正是要的形状。

**规矩再收紧：判断「死没死」必须看类型与成员，不看文件名；**
文件级结论一律要用 `Select-String -CaseSensitive 类型名` 复核过才允许写进文档。
