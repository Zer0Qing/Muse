一个需要记下来的教训：我一度断言"宿主 8 项能力只实现了 4 项"，那是**grep 只匹配 `override fun`、漏了 `override suspend fun`** 造成的假警报。
以后凡是"某能力没人实现"这类结论，必须先确认搜索模式覆盖 `suspend`，否则会把好代码当缺陷去"修"。
同类错误这轮又犯一次：P3 写成「没有测试锁」，读代码才发现引擎档位早测透了 ——
**缺口要从读代码确认，不能从「我 grep 到了什么」反推**。

## 1. 本轮已修（入口隐藏契约）

小手机的可见性此前**只有注释在传达，而两处注释互相矛盾**：

- `FeatureFlags` 顶部写"不能只藏 UI 而留着路由"；
- `MINI_PHONE_ENTRY` 自己写"搜索仍能命中、链接仍能进入"；
- `ChatNavGraph` 留着"本版不对外发布"的旧注释；
- `ARCHITECTURE_MAP` 写着 `MINI_PHONE = false`、"当前不发版" —— 与代码（`= true`，模块与路由都在包里）相反。

真实设计是：**入口藏（首页 `MINI_PHONE_ENTRY`、设置 `browseVisible`），路由留（`MINI_PHONE`）**。
已做三件事：

1. 两处注释/文档按真实设计重写，并解释**为什么允许留路由**（模块在包里却裁掉路由，
   会让搜索命中与恢复的导航栈指向不存在的页面，比"能进但没入口"更难解释）；
2. 新增 `MiniPhoneVisibilityContractTest`（4 例）把契约钉成断言：
   首页过 ENTRY、设置过 `browseVisible && MINI_PHONE`、路由过 `MINI_PHONE` **且不得过 ENTRY**、
   `MOMENTS == MINI_PHONE`；
3. 验证：feature 族 4 例全绿，`:app:detekt` 仍为 18 条（零新增）。

## 2. 接下来的顺序（按"风险 × 可验证性"排）

### P1 协作 UI 四个面 —— ✅ 已完成（8 条真机 Compose 测试，全绿）

四个面此前**在测试里一次都没出现**，现在各有渲染断言 + 交互断言：

| 测试类 | 钉住的行为 |
|---|---|
| `TaskCardSurfacesDeviceTest`（7 例） | 空链路显示提示且**不画卡片框**；链路标题 + 「节点 N」计数 + 暂停节点必须显示「等待确认」（这是用户唯一知道要动手的地方）；任务卡**默认折叠**，点整行才展开明细；点取消按钮回调收到**对应那条**的 taskId；确认对话框点「批准继续」回 `APPROVE`、点「取消委派」回 `CANCEL`；`pauseRequest == null` 时什么都不画 |
| `AgentDmScreenDeviceTest`（1 例） | 页面能 compose；返回键真的把控制权交回调用方 |

跑出来的两个事实（都是**既定设计**，不是 bug，但现在被测试钉住了）：

- 任务卡默认折叠：明细行一上来不该占屏；
- 确认对话框的选项来自 `PauseRequest.options`，**默认只有「批准/拒绝」**，
  不含「取消委派」—— 所以测试自己把三项摆全，而不是假设界面一定会给。
  （第一版就是因为假设了有 CANCEL 才红。）

断言一律绑**资源 id 而不是中文串**：换语言或改文案时测试不该跟着红，
"该出现的文字没出现"才是真正的回归信号。`AgentDmScreen` 那条也刻意**不断言空态**——
那取决于设备上此刻有没有私信，把数据状态写进断言会让真机测试随机红。

验收达成：四个面各有渲染 + 交互断言，`:app:detekt` 保持 18 条零新增，
`am instrument` **OK (8 tests)**。

### P2 小手机覆盖不均 —— 🔶 进行中（本轮补 1 条，另开一条明确的技术活）

**先更正路线里我自己写错的规模**：按"实现文件名在测试目录里出现 0 次"统计，
零提及的文件不是 8 个而是 **22 个**，其中包含 `ChatSendController`(333)、

且 `MiniPhoneChatViewModelTest` 通过 `viewModel.send(...)` 真跑过它的主路径

本轮已补：`blankInputStoresNothingAndNeverAsksTheCharacter`（空白输入不落库也不问角色）。

尝试补"同一句话连发两次不另起一轮"时失败并**已撤回**：VM 那套 `GatedHost` 的闸门

测试超时。这不是断言写太严，是**测试脚手架不合用**。
→ 待办（✅ 已完成，见上）：给 `ChatSendController` 建直接测试，覆盖 `claimedRounds`、`isDuplicateSubmission`、`NO_RESPONDER`、`QUEUE_CLOSED → FAILED` 四条边界。

### ✅ 四条边界已落地（2026-11-04 第二次尝试）

`ChatSendControllerTest` 4 例全绿，`:miniphone` 310 → **314 例**：
重复提交只落库不再问角色、群里没人可接定稿「已发出」、队列已关标「发送失败」、
已认领的一轮不被 `resend` 再跑（状态也不被改回「发送中」）。

**真因更正**：上一轮我写"下一步先把被吞的异常捞出来"。捞了 —— 挂上
`CoroutineExceptionHandler` 之后**一条异常都没有**：生产代码没问题。
红的原因是**测试作用域用了自带虚拟时间调度器的 `TestDispatcher`**：
落库走 Room 的 `withContext(Dispatchers.IO)`，恢复被排进那个调度器自己的队列，
而 `runCurrent()` / `advanceUntilIdle()` 推进的是 `runTest` 那条队列，于是永远不落库。
最终配方：`Dispatchers.Unconfined + Job + CoroutineExceptionHandler`，
等待用真实轮询（`settleUntil`）而不是虚拟时间。

教训写进类注释了：**harness 的调度器与等待方式必须和被测代码的线程模型一致**；
"看起来像被吞的异常"（`UncaughtExceptionsBeforeTest`）不能当成根因，要先把异常捞出来证伪。

### 上一轮那次尝试留下的记录（保留，别重复绕路）

曾经试过的解释：

假件本身没问题（`MiniPhoneHost` 用 `flow{}` 计调用次数 + `CompletableDeferred` 当闸门、
`ChatMessageWriter` 用真内存 Room、`MpImageStore(directory=tmp, openStream={null})`），
但四条全红：**库里一条消息都没落**。当时逐次排掉的假设：

| 试过的解释 | 结果 |
|---|---|
| 断言太严（等回复落库那段） | 删掉那段后仍然红 —— 不是断言问题 |
| `runBlocking` 下没人排空测试调度器 | 换 `runTest` 后仍红 |
| 作用域自带新调度器，`runCurrent()` 排不到它 | 改 `UnconfinedTestDispatcher(testScheduler)` 与 runTest 共用后仍红 |
| **真正的线索** | 其中一条报 `UncaughtExceptionsBeforeTest`：harness 里有**未捕获异常**被作用域吞掉，所以"什么都没落库"只是它的下游表现 |

**下一次的第一步不是再改调度器**，而是把那个异常捞出来：给控制器作用域挂
`CoroutineExceptionHandler` 打印，或干脆不用 `launch`（`send()` 内部是 `scope.launch`，
所以在测试里给它一个会立刻崩就报的 Job）。异常一现，四条边界大概率一次就绿。

这一轮没有把红的东西留下：**测试文件已删除**，`:miniphone` 回到 310 例全绿。

### P3 语音链路两端一致性 —— ✅ 已完成（判定收成一处 + 矩阵测试）

**先更正我自己**：这条在路线里写成"不变式没有测试锁"，读代码后并不准确 ——
`OneShotAsrTranscriberTest` 早把 `supportsFileTranscription()` 的各引擎档位钉得很细
（Whisper/AGNES 支持；SYSTEM/DASHSCOPE/STEP/REALTIME 不支持；空 key；非 http baseUrl）。
真正缺的不是测试，是**两个出口共用同一判据**这件事：`transcribe()` 里三个 `return null`
与 `supportsTranscription()` 里一个表达式各写一遍 —— 条件写第二遍，就是一个可以分家的缝。

小手机据此决定麦克风是置灰还是点亮。一旦两边漂移，用户看到的是"能按，按完永远转不出字"，
而这种东西在真机上极难被注意到。所以做法是**消掉缝**，不是补一层重复测试：

```kotlin
internal fun asrGate(config: AsrConfig?, hasAudio: Boolean): AsrGate
internal enum class AsrGate { GO, EMPTY_AUDIO, NOT_CONFIGURED, UNSUPPORTED_ENGINE }
```

- 两个出口都只问 `asrGate` 一次；
- **判定顺序也是内容**：先问有没有音频，再问有没有配置。
  空音频时报"你没配识别服务"，用户会去设置页白找一圈，而真实原因是那段录音是空的；
- `hasAudio` 只允许 `transcribe` 传 false：界面问"支不支持"不该因为此刻手上没音频就答不支持；
- 新增 4 例矩阵测试，其中一例**遍历 `AsrProviderType.entries`**：
  以后新加一档引擎，这条会逼着回答"它到底能不能整段转写"，而不是两边各答各的。

`asr` 族 19 例全绿，`:app:detekt` 保持 18 条。

### P4 协作语义的显式化 —— 🔶 第一批已落地（token 预算 + 委派上下文）

**协作规则一览表**（数值只有一处出处；改数值必须同时改对应测试，否则测试会红）：

| 规则 | 数值 | 出处 | 钉在哪 |
|---|---|---|---|
| 子 agent 默认 token 预算 | 60,000（prompt+completion 合计） | `AgentTokenBudget.DEFAULT_SUBAGENT_BUDGET` | `AgentTokenBudgetTest` |
| 全局并发子 agent 上限 | 8（注释写明：上限可到 256，手机端保守取 8） | `AgentConcurrencyLimiter.DEFAULT_MAX_CONCURRENT` | 已有测试（6 处提及） |
| 单生命周期累计派发上限 | 200（超过直接拒，防失控） | `AgentConcurrencyLimiter.DEFAULT_MAX_TOTAL` | 已有测试 |
| 委派链最深几层 | **3**（到深度就不再把 `delegate_agent` 传给子 agent，防递归爆炸） | `SkillDelegateAgentImpl.MAX_DELEGATE_DEPTH` | 已有测试（4 处提及深度） |
| 等待槽位的轮询间隔 | 100ms | `AgentConcurrencyLimiter.POLL_INTERVAL_MS` | 实现细节，不钉 |
| 委派默认超时 | 60s | `DelegationContract.DEFAULT_TIMEOUT_SEC` | `DelegationContract` 相关测试（13 处提及） |
| 暂停策略默认 | `pauseOnHighRisk = true`，其余三类默认关；超时 300s **自动拒绝** | `DelegationPauseManager.PausePolicy` | `DelegationPauseManagerTest`（26 处提及） |
| 一次委派带的上下文条数 | 最近 **8** 条 | `DelegationContextBuilder.DEFAULT_MAX_MESSAGES` | `DelegationContextBuilderTest` |
| 上下文里不许出现的字段 | 孤儿 `toolCalls`、`reasoning`、图片/语音/引用/心情/引用块等一律清空 | 同上 | 同上 |

本轮新增 12 例（两个测试类各 6 例），钉的是**此前完全没测试**的两个单元：

- **`AgentTokenBudget`**（测试里 0 提及）：
  `of(null/0/负数)` 一律"不限制"而不是"预算为 0"；预扣被拒时**一分都不记账**；
  `usage == null` 不能判耗尽 —— 很多 Provider 不回 usage，把它当烧完会让所有委派第一轮就断；
  恰好等于上限即耗尽；余额永不为负。
- **`DelegationContextBuilder`**（测试里 0 提及）：
  截的是**最近** N 条（截反方向会让子助手看不见用户刚说的话）；空白内容不进上下文；
  默认**整条丢掉带图消息**；显式允许带图时仍剥掉 `toolCalls`/`reasoning`/语音
  （孤儿 toolCalls 会被 Provider 直接拒，表现为"委派没结果"，很难归因）。

一处我自己写反的测试：`纯文本通路…清空` 第一版给的消息带了 `imageUrls` —— 那条在文本通路上
**整条被丢弃**，根本走不到剥字段那步。这不是断言太严，是我对产品行为理解错；
改成"没有图但带旁路字段"的消息，并把"带图整条丢"留给已有的那条测试管。

余下要显式化的：深度 3 与并发 8 目前只有零散提及，值得补成"到深度就不再给 delegate_agent"的
**行为**断言（现在更像常量断言）。

### P5 发布面上的说法与实际一致

小手机与网页版属于"代码在、入口藏、发行材料不提"。每次发版要复核：
`manifest.json`/release notes 没写它们，而 `ARCHITECTURE_MAP`/`HANDOFF` 写清了为什么。
本轮已把第一条矛盾消掉，后续每次动旗标都要复跑 P1 的契约测试。

## 3. 明确不做

- 不把路由改成受 `MINI_PHONE_ENTRY` 控制（见 §1 的理由）；
- 不给小手机或协作 UI 补"截图级"快照测试 —— 渲染细节靠真机看，逻辑靠断言；
- 不在这一批动 `:app:detekt` 剩下 18 条结构性违规（另案，已有进度记录）。
