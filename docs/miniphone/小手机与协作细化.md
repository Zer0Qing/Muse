### ✅ 四条边界已落地（2026-11-04 第二次尝试）

`ChatSendControllerTest` 4 例全绿，`:miniphone` 310 → **314 例**：
重复提交只落库不再问角色、群里没人可接定稿「已发出」、队列已关标「发送失败」、
已认领的一轮不被 `resend` 再跑（状态也不被改回「发送中」）。

**真因更正**：上一轮我写"下一步先把被吞的异常捞出来"。捞了 —— 挂上
`CoroutineExceptionHandler` 之后**一条异常都没有**：生产代码没问题。
红的原因是**测试作用域用了自带虚拟时间调度器的 `TestDispatcher`**：
落库走 Room 的 `withContext(Dispatchers.IO)`，恢复被排进那个调度器自己的队列，
而 `runCurrent()` / `advanceUntilIdle()` 推进的是 `runTest` 那条队列，于是永远不落库。
最终配方：`Dispatchers.Unconfined + Job + CoroutineExceptionHandler`，
等待用真实轮询（`settleUntil`）而不是虚拟时间。

教训写进类注释了：**harness 的调度器与等待方式必须和被测代码的线程模型一致**；
"看起来像被吞的异常"（`UncaughtExceptionsBeforeTest`）不能当成根因，要先把异常捞出来证伪。

### ⚠️ 已确认的既有 flake：跨测试类共享全局 `Dispatchers.Main`

现象（一次全量跑里出现 2 条，单独跑与重跑全绿）：

```
IllegalStateException: Dispatchers.Main is used concurrently with setting it
  at kotlinx.coroutines.test.internal.TestMainDispatcher$NonConcurrentlyModifiable.concurrentRW
  MiniPhoneChatImageSendTest :: profileFillsTheOwnSideNameAndAvatar
  MiniPhoneChatViewModelTest :: unknownCharacterFallsBackToThePlaceholderName
```

判据：同一命令第二次跑 **331 例 / 0 失败**；两个类单独跑也全绿 —— 是调度依赖的顺序竞态，
不是断言问题，也与本轮改动无关（本轮新文件都不碰 Main）。
成因方向：某处 `Dispatchers.setMain(...)` 之前，上一留下的协程还在读 Main。
**这比"测试红"更值得修**：一有 flake，真回归就会被当成"又飘了"混过去。

#### 已经试过一种"看起来很合理"的修法，**它是错的**，别再走

试过：全模块共用一个 eager Main（`SharedTestMain.install()` 只装不拆，7 个类各自
`setMain`/`resetMain` 全去掉）。听起来正好治"换 Main 时有人在读"。

结果：`:miniphone:testDebugUnitTest` 从 1 条随机红变成 **11 条稳定红**，红的还全是
Compose UI 测试（`MiniPhoneChatImageUiTest`、`MiniPhoneChatUiTest`、
`MiniPhoneGroupChatUiTest`、`MiniPhoneMomentsUiTest`）。

原因：**`createComposeRule()` 自己会接管 `Dispatchers.Main`**（它要驱动帧时钟与 `awaitIdle`）。
一个"永久装着不拆"的 Main 与它抢同一个全局，Compose 的规则就失效了。
也就是说这个模块里同时存在两类对 Main 的合法要求：
VM 测试要"设了别拆、拆了别撞"，Compose 测试要"这条测试期间由我独占"。

所以约束条件是：**不能动全局 Main 的安装/卸载策略**，只能消除"跨类遗留的协程"本身 ——
候选做法（下一轮验，别一次改 7 个类）：
  1. 在 VM 类 `@After` 里先取消它自己创建的作用域 / 清掉 ViewModel，再 `resetMain()`
     （治泄漏本身，不碰 Compose 的规则）；
  2. 或把 VM 类与 Compose 类拆到不同 fork（Gradle 任务级隔离，改动大、收益确定）；
  3. 判据：同一命令连跑 3 次全绿才算修好，跑一次绿不算。

已回滚，`:miniphone` 331 例 / 0 失败。

**频率实测**（决定它排多高）：回滚后用 `--rerun-tasks` 连跑两次全量，加上之前那次，共 **3 次全绿**；而此前约 5 次全量里出现过 **1 次**（2 条红）。也就是频率约 1/5 —— 不至于天天红，但**足够让一次真回归被当成 flake 放过去**。

据此定优先级：按「要修，但不紧急到打断一切」处理 —— P2b 覆盖率继续推，隔离修复单独一小步做；**验收判据是连跑 3 次全绿**，跑一次绿不算修好。

#### ✅ 已修好（同一轮内）：治的是泄漏，不是全局 Main

最终做法是候选 1 的完整版：**6 个创建 ViewModel 的测试类，各自在 `@After` 里先回收自己造的 VM，
再 `resetMain()`**。`ViewModel.clear()` 是 internal 调不到，所以套一个 `ViewModelStore`：
建 VM 时 `track()` 挂进去，收尾 `createdVmStore.clear()`。

为什么 VM 会害到**别的类**：`viewModelScope` 用 `Dispatchers.Main.immediate`，
VM 不回收 → 它的收集协程还活着并会再读全局 Main，下一个类 `setMain` 就撞上
kotlinx-coroutines-test 的"不许并发换 Main"检查。

**机制级前后对照**（比"连跑多次全绿"更硬的证据）：

| 阶段 | 结果 |
|---|---|
| 修了 5 个类、**漏 Moments** | 一次全量里 Moments **确定性红 2 条**，栈分别是 `resetMain` 与遗留协程的 `isDispatchNeeded` —— 它自己踩自己 |
| 补上 Moments（两处构造都挂进 store） | 编译 + 测试 + `:miniphone:detekt` 全绿，随后 `--rerun-tasks` **连跑 5 次全绿**（累计 6 次） |

泄漏源是谁，红就出现在谁身上；每个类把自己的 VM 收回，竞态窗口就不存在了。
全程**没有动全局 Main 的安装策略**，Compose 测试规则照样独占它。

工具层面一条收获：脚本一律要求"锚点唯一"，几次在写盘前挡下歧义命中
（`createViewModel` 的收尾形状与 `seedThread` 相同 → count==2 直接拒绝修改）。
这类多点编辑没有断言，就是静默改错地方。

### P3 语音链路两端一致性 —— ✅ 已完成（判定收成一处 + 矩阵测试）

**先更正我自己**：这条在路线里写成"不变式没有测试锁"，读代码后并不准确 ——
`OneShotAsrTranscriberTest` 早把 `supportsFileTranscription()` 的各引擎档位钉得很细
（Whisper/AGNES 支持；SYSTEM/DASHSCOPE/STEP/REALTIME 不支持；空 key；非 http baseUrl）。
真正缺的不是测试，是**两个出口共用同一判据**这件事：`transcribe()` 里三个 `return null`
与 `supportsTranscription()` 里一个表达式各写一遍 —— 条件写第二遍，就是一个可以分家的缝。

小手机据此决定麦克风是置灰还是点亮。一旦两边漂移，用户看到的是"能按，按完永远转不出字"，
而这种东西在真机上极难被注意到。所以做法是**消掉缝**，不是补一层重复测试：

```kotlin
internal fun asrGate(config: AsrConfig?, hasAudio: Boolean): AsrGate
internal enum class AsrGate { GO, EMPTY_AUDIO, NOT_CONFIGURED, UNSUPPORTED_ENGINE }
```

- 两个出口都只问 `asrGate` 一次；
- **判定顺序也是内容**：先问有没有音频，再问有没有配置。
  空音频时报"你没配识别服务"，用户会去设置页白找一圈，而真实原因是那段录音是空的；

本轮新增 12 例（两个测试类各 6 例），钉的是**此前完全没测试**的两个单元：

- **`AgentTokenBudget`**（测试里 0 提及）：
  `of(null/0/负数)` 一律"不限制"而不是"预算为 0"；预扣被拒时**一分都不记账**；
  `usage == null` 不能判耗尽 —— 很多 Provider 不回 usage，把它当烧完会让所有委派第一轮就断；

### ✅ P4 第二批（并发闸门与深度规则的行为化）

`AgentConcurrencyLimiterTest` 5 例 + `DelegateDepthTest` 3 例。

**深度规则顺手做了个小重构**：原来入口用 `depth > 3` 拒、下发工具用 `depth < 3` 给，
两处各写一个字面量 3 —— 漂了不会编译报错，只会得到"递归到第 5 层还没停"这种压穿本地模型的现场。
现在统一成 `DelegateDepth.allowsEntry(depth)` / `shouldOfferDelegateTool(depth)`，一个出处。
测试还钉住两条判定**为什么不能相等**：入口上限 = 工具上限 + 1，
否则最后一层还能委派，只能靠入口硬拒（那是 ThreadLocal 没归零的异常兜底，不是常规停止手段）。

**并发闸门此前从没被测过**：其它测试只是"造一个 limiter 塞给被测对象放行"或 mockk 直通。
现在钉住四件真会出事的事：

| 断言 | 出事时长什么样 |
|---|---|
| 第 3 个必须排队（`maxConcurrent = 2`，两个持有者挂住不放） | 不生效 → 十几个子 agent 同时压本地模型，整机卡死 |
| 任务抛异常也要归还槽位（异常后下一个 2s 内必须能跑通） | 漏槽位 → 跑到第 N 次委派起**永久排队**；进程内计数，**重启应用也不会恢复** |
| 累计超 `maxTotal` 直接拒，且原因里带"上限"字样 | 失控递归派发 |
| 正常使用后计数归零、不会变负 | 信号量失效 |
| 默认值仍是 8 / 200 | 改这两个数等于改全体委派的资源上限 |

一条自我修正值得记：并发那条测试**第一版写错了场景** —— 我只让第一个持有者挂住，第二个立刻跑完归还了槽位，
于是第三个"合法地"进了来，断言失败。诊断打印 `started=[a, b, c] active=1` 直接点破是我把测试写成了
允许的情形。**这不是产品 bug，是测试没构造出它声称在测的条件。**

全量：`:app:testDebugUnitTest` **4546 例 / 0 失败**（`io.zer0.muse.tools` 族 770 例），`:app:detekt` 仍 18 条。

## 15. 待查：群聊"最近发言者"依赖首屏是否已落地（怀疑，未定论）

一次全模块里 `aNamedMemberPlusTheRecentSpeakerAreExactlyTheTwo` 给出 `[c2, c3]`（期望 `[c2, c4]`），
单跑 3 次与其后的全模块都绿 ⇒ 时序相关而非常驻失败。

**从库里读**（与分页共用同一把写锁），而不是继续靠界面状态。
