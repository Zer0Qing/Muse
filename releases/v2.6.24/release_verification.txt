## 构建来源与工作区状态（重要，不隐瞒）
构建命令: ./gradlew :app:assembleRelease -PversionName=2.6.24 -PversionCode=288
构建工作树: **主工作树**（不是 v2.6.23 那种 --detach 干净树）。构建时 HEAD=d58416fa，工作树另含未提交改动。

1. **包与 tag 不同源，这一条明写。** 28a6ad98 提交了本轮全部 app 侧修复（49 个文件）与发布记录，
   但包是在它之前、从带未提交改动的工作树构建的；包里还含**未提交的小手机改动**：
   MiniPhoneDb 版本 6（tag 上是 5）、mp_inner_voice 与 mp_call_session 表、R3 通话草稿
   （MpCallKind / MpCallStore / MpCallSessionDao / MpCallSessionEntity）、宿主侧的心声实现
   （AppMiniPhoneHost.composeInnerVoice）。这些按要求本轮不进仓库，下个版本随小手机一起发。
2. **为什么这不构成本版的用户风险（已核对，不是推测）：**
   - FeatureFlags.MINI_PHONE=false 且 MINI_PHONE_ENTRY=false：首页与设置无入口、路由不注册；
   - R8 已把小手机 UI 摇掉：dex 里搜不到 MiniPhoneShell；
   - miniphoneModule 的 single 全部惰性创建，启动路径只调 MiniPhoneMomentScheduler.stop()，
     而它只做 WorkManager.cancelUniqueWork + 取消私信排期，不解析 Koin、不开数据库；
   - 因此 mp_inner_voice / mp_call_session 只作为 dex 字符串存在，用户设备上不会创建 v6 库；
     旧装机已有的 v5 库不会被迁移，也不会出现"高版本库被低版本源打开"的降级路径。
   - 结论：包内多出的这部分是**不可达代码**，不影响本版行为；但它确实使 tag 无法逐字节复现该包。
3. gitignore 的 pack 产物（app/src/main/jniLibs/、muse-python-assets.zip、muse-runtime-assets.zip）
   沿用主工作树已准备好的产物：本机是 Windows，跑不了 CI 在 Linux runner 上的 patchelf 步骤。
   网页 bundle 同样取主树的 web/apps/client/dist，**没有**像 v2.6.23 那样在干净树里 npm ci && npm run build
   重建（这就是 js 哈希与那次候选不同的原因）。包内 bundle 因此对应主树当时的 dist，而非 sourceCommit 重建结果。
